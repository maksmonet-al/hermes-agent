# Техническое задание: многоуровневая оркестрация Hermes Agent

## 1. Цель

Настроить Hermes Agent как главный оркестратор с многоуровневой маршрутизацией задач между несколькими моделями и специализированными CLI-исполнителями.

Главная задача — получить систему, в которой:

- основная модель Hermes работает постоянно и принимает большинство решений;
- дешёвые подзадачи делегируются недорогой модели;
- действительно сложные архитектурные и спорные решения эскалируются на более сильную модель;
- разработка выполняется через Codex CLI;
- review, тестирование и контроль roadmap выполняются через Sol 5.6 Medium из подписки;
- главный Hermes сохраняет управление workflow и принимает итоговые решения;
- расход дорогих моделей минимизируется без заметной потери качества.

---

## 1.1. Временная конфигурация review

На текущем этапе Qwen CLI НЕ используется, так как лимиты подписки/токенов недоступны.

До восстановления Qwen роль независимого reviewer/tester выполняет:

```text
Sol 5.6 Medium
```

через существующую subscription-backed авторизацию.

После восстановления Qwen архитектура должна позволять вернуть Qwen в роль reviewer без перестройки остальных компонентов.

## 3. Роли моделей

### 3.1. Terra 5.6 High — главный оркестратор

Terra является основной моделью Hermes.

Обязанности:

- принимать все входящие пользовательские запросы;
- понимать конечную цель пользователя;
- декомпозировать сложные задачи;
- выбирать исполнителя для каждой подзадачи;
- контролировать состояние проекта;
- читать и учитывать roadmap;
- контролировать последовательность этапов;
- собирать результаты субагентов и CLI-исполнителей;
- решать, требуется ли дополнительная проверка;
- принимать итоговое решение;
- формировать финальный ответ пользователю;
- при необходимости эскалировать сложный вопрос в Sol.

Terra не должна выполнять тяжёлую механическую работу самостоятельно, если её можно безопасно делегировать.

Предпочтительный reasoning level:

```yaml
reasoning_effort: high
```

Если фактическая конфигурация Hermes использует другое имя параметра, необходимо определить правильный синтаксис по установленной версии Hermes и использовать его.

---

### 3.2. DeepSeek Flash — модель стандартных субагентов

DeepSeek Flash используется как дешёвая рабочая модель для Hermes subagents.

Типичные задачи:

- разведка файлов проекта;
- поиск по репозиторию;
- поиск определений, функций, классов и зависимостей;
- анализ структуры директорий;
- сбор фактов;
- подготовка кратких summary;
- поиск повторяющихся проблем;
- изучение логов;
- первичный анализ конфигураций;
- подготовка списка релевантных файлов;
- массовые однотипные проверки;
- простая web/data extraction работа;
- подготовка контекста для Terra;
- другие хорошо изолированные задачи, не требующие стратегического решения.

DeepSeek НЕ должен:

- самостоятельно менять архитектуру проекта;
- принимать критические продуктовые решения;
- менять roadmap;
- утверждать крупные refactoring decisions;
- выполнять необратимые действия без решения Terra;
- заменять Terra как главного оркестратора.

---

### 3.3. Sol 5.6 Medium — reviewer/tester

Sol 5.6 Medium используется как независимая модель проверки после работы Codex CLI.

Роль:

- code review;
- tests;
- roadmap compliance;
- regression detection;
- acceptance criteria validation;
- scope control.

Sol Medium не должен принимать на себя роль главного оркестратора и не должен заменять Codex как основного разработчика.

Предпочтительный reasoning:

```yaml
reasoning_effort: medium
```

---

### 3.4. Sol 5.6 High — экспертная эскалация

Sol используется НЕ как основной агент и НЕ как стандартный subagent.

Sol — старший эксперт для сложных, дорогих по последствиям или неоднозначных решений.

Создать отдельный skill/tool с рабочим названием:

```text
ask_sol
```

или:

```text
expert_escalation
```

Допустимо выбрать другое понятное имя, если оно лучше соответствует архитектуре Hermes.

Terra должна иметь возможность вызвать этот инструмент самостоятельно.

Предпочтительный reasoning level Sol:

```yaml
reasoning_effort: high
```

## 4. Когда Terra должна обращаться к Sol

Эскалация разрешена, когда выполняется хотя бы одно из условий:

1. Требуется важное архитектурное решение.
2. Решение затрагивает несколько крупных компонентов системы.
3. Ошибка может привести к значительному объёму переделок.
4. Есть несколько сильных вариантов реализации с существенными trade-offs.
5. Результаты разных агентов противоречат друг другу.
6. Codex и Sol 5.6 Medium не могут прийти к устойчивому решению после одного полного цикла разработки и review.
7. Terra имеет низкую уверенность в своём решении.
8. Требуется глубокий анализ сложной причины бага.
9. Имеется риск потери данных, нарушения совместимости или серьёзной деградации архитектуры.
10. Требуется решение по масштабной миграции.
11. Нужно проверить критически важный технический план до начала дорогостоящей реализации.
12. Пользователь явно просит подключить Sol / старшую модель / экспертный reasoning.

---

## 5. Когда Sol вызывать НЕ нужно

Не использовать Sol для:

- обычных вопросов пользователя;
- простого написания текста;
- поиска файлов;
- чтения логов;
- стандартного bugfix;
- простого CRUD;
- небольших frontend-изменений;
- обычных тестов;
- форматирования;
- переименования;
- стандартной настройки;
- задач, которые уверенно решает Terra;
- задач, которые можно делегировать DeepSeek;
- задач разработки, которые должен выполнить Codex;
- стандартного review, которое выполняет Sol Medium.

Главный принцип:

> Sol должен использоваться редко и только тогда, когда его дополнительное качество оправдывает дополнительную стоимость.

## 6. Формат контекста для Sol

Нельзя без необходимости передавать Sol весь накопленный conversation context.

Перед вызовом Sol Terra должна сформировать компактный пакет:

```markdown
# Goal

Что требуется решить.

# Current State

Текущее состояние проекта или задачи.

# Constraints

Ограничения, требования, совместимость, инфраструктура.

# Evidence

Проверенные факты, выводы субагентов, логи, тесты.

# Relevant Files

Только релевантные файлы и фрагменты.

# Options

Какие варианты уже рассматриваются.

# Risks

Какие риски имеются.

# Exact Question

Конкретный вопрос, на который должен ответить Sol.
```

Sol должен вернуть:

```markdown
# Recommendation

Рекомендуемое решение.

# Why

Ключевые причины.

# Trade-offs

Минусы и компромиссы.

# Risks

Что может пойти не так.

# Validation

Как проверить решение.

# Confidence

High / Medium / Low
```

После ответа Sol окончательное решение остаётся за Terra.

## 7. Codex CLI — основной разработчик

Codex CLI уже используется как специализированный исполнитель разработки.

Hermes должен вызывать Codex CLI для:

- реализации новых функций;
- изменения существующего кода;
- исправления багов;
- refactoring;
- создания migrations;
- разработки backend/frontend;
- реализации API;
- написания тестов вместе с реализацией, когда это необходимо;
- изменения конфигурации проекта.

Перед запуском Codex Terra должна подготовить чёткую задачу.

Минимальная структура задания Codex:

```markdown
# Task

Что требуется сделать.

# Goal

Какой результат должен быть достигнут.

# Project Context

Краткий необходимый контекст.

# Relevant Files

Файлы, найденные разведкой.

# Constraints

Что нельзя ломать или менять.

# Acceptance Criteria

Проверяемые критерии готовности.

# Tests

Какие тесты необходимо выполнить.

# Do Not

Явные запреты и ограничения.
```

Codex не должен самостоятельно менять roadmap или расширять scope задачи без разрешения Terra.

## 8. Sol 5.6 Medium — review, tests и контроль roadmap

Sol 5.6 Medium временно выполняет роль независимого reviewer/tester вместо Qwen CLI.

Использовать Sol Medium для:

- независимого code review;
- анализа git diff;
- поиска ошибок и regressions;
- проверки acceptance criteria;
- проверки архитектурной согласованности;
- проверки соответствия roadmap;
- выявления scope creep;
- проверки, не изменил ли Codex лишние файлы;
- проверки migrations;
- проверки API compatibility;
- проверки безопасности изменений;
- анализа и запуска безопасных тестов, если это доступно через текущую интеграцию;
- итогового verdict по работе Codex.

Sol Medium НЕ является основным разработчиком.

Sol Medium не должен самостоятельно исправлять код без явного решения Terra.
Если review завершился FAIL, Terra должна сформировать targeted fix task и повторно вызвать Codex CLI.

Предпочтительный reasoning:

```yaml
reasoning_effort: medium
```

Использовать модель через существующую subscription-backed авторизацию. Не использовать API/OpenRouter, если подписочный способ уже работает и подходит для этой роли.

Формат результата:

```markdown
# Verdict

PASS / PASS WITH NOTES / FAIL

# Critical Issues

Критические проблемы.

# Major Issues

Существенные проблемы.

# Minor Issues

Некритичные замечания.

# Roadmap Compliance

Соответствует ли изменение roadmap.

# Test Results

Результаты тестов.

# Recommended Next Action

Что делать дальше.
```

## 9. Обязательный development workflow

Для задач разработки использовать следующий цикл.

### Этап 1. Понимание задачи

Terra:

1. определяет цель;
2. определяет scope;
3. читает roadmap и project instructions;
4. проверяет существующую документацию.

### Этап 2. Разведка

Если требуется изучение проекта:

Terra -> DeepSeek subagent(s)

Получить:

- relevant files;
- architecture summary;
- dependencies;
- likely impact;
- existing implementation;
- possible risks.

### Этап 3. План

Terra формирует план реализации.

Если решение архитектурно сложное — Terra может вызвать Sol.

### Этап 4. Реализация

Terra -> Codex CLI.

Codex реализует только утверждённый scope.

### Этап 5. Review

Terra -> Sol 5.6 Medium.

Sol Medium:

- анализирует diff;
- проверяет roadmap;
- запускает/проверяет тесты;
- выдаёт verdict.

### Этап 6. Исправления

Если Sol 5.6 Medium вернул FAIL:

Terra анализирует замечания.

Если замечания обоснованы:

Terra -> Codex CLI на исправление.

После исправлений:

Terra -> Sol 5.6 Medium повторно.

### Этап 7. Эскалация

Если после разумного цикла остаётся спорная архитектурная проблема:

Terra -> Sol High.

Sol даёт экспертное решение.

Terra определяет дальнейший шаг.

### Этап 8. Завершение

Terra:

- убеждается, что acceptance criteria выполнены;
- проверяет, что roadmap не нарушен;
- фиксирует итог;
- сообщает пользователю результат.

## 10. Ограничение бесконечных циклов

Нельзя допускать бесконечный цикл:

```text
Codex -> Sol Medium -> Codex -> Sol Medium -> ...
```

По умолчанию:

- первый Codex implementation;
- первый Sol Medium review;
- один или два targeted fix cycles.

Если одна и та же существенная проблема сохраняется после двух исправлений, Terra должна:

1. остановить цикл;
2. провести самостоятельный анализ;
3. при необходимости вызвать Sol;
4. сформировать новое решение.

---

## 11. Работа с roadmap

Roadmap является источником ограничений проекта.

Перед крупной задачей Terra должна:

- найти roadmap;
- прочитать актуальный этап;
- определить, входит ли задача в текущий scope.

Sol Medium обязан проверять изменения относительно roadmap.

Если пользователь прямо изменил приоритет или roadmap, более новая явная команда пользователя имеет приоритет.

Не изменять roadmap автоматически только потому, что разработчик выбрал другой путь.

---

## 12. Модельная маршрутизация

Не использовать ненадёжную автоматическую маршрутизацию только по длине prompt или ключевым словам как основной механизм принятия решений.

Основной routing выполняет Terra через явные tools/skills.

Целевая логика:

```text
Routine isolated research
    -> DeepSeek Flash

Code implementation
    -> Codex CLI

Review / testing / roadmap validation
    -> Sol 5.6 Medium

Normal reasoning / orchestration
    -> Terra High

High-impact / ambiguous / low-confidence reasoning
    -> Sol High
```

---

## 13. Fallback не путать с escalation

Если Hermes имеет штатный fallback provider/model:

- использовать fallback только для отказоустойчивости;
- rate limit;
- provider outage;
- authentication failure;
- temporary model unavailability.

Fallback НЕ должен считаться заменой механизма Sol escalation.

---

## 14. Требования к реализации в Hermes

Hermes должен самостоятельно:

1. Определить фактическую версию установленного Hermes Agent.
2. Найти текущий конфигурационный файл.
3. Сделать резервную копию конфигурации перед изменениями.
4. Проверить текущего provider основной модели.
5. Проверить доступность Terra.
6. Проверить доступность Sol.
7. Проверить доступность DeepSeek Flash.
8. Проверить текущую конфигурацию delegation/subagents.
9. Проверить существующие skills.
10. Проверить существующую интеграцию Codex CLI.
11. Проверить существующую интеграцию Sol 5.6 Medium.
12. Не дублировать уже существующие рабочие skills.
13. Использовать штатные механизмы Hermes там, где они доступны.
14. Там, где штатного механизма нет, создать минимальный надёжный custom skill/tool.
15. Не изменять unrelated configuration.
16. Не удалять существующие рабочие integrations.
17. Не раскрывать API keys, OAuth tokens или другие secrets в логах и отчётах.

## 16. Provider abstraction

Не хардкодить provider без необходимости.

Модель может использоваться:

- через OpenAI provider;
- OpenRouter;
- subscription-backed CLI;
- другой уже настроенный provider.

Hermes должен сначала определить, как модели реально подключены на текущем сервере.

Конфигурация должна ссылаться на фактические рабочие model IDs.

Если имя модели из задания не совпадает с реальным model ID provider:

1. определить корректный ID;
2. использовать корректный ID;
3. указать это в итоговом отчёте.

## 17. Reasoning levels

Целевая логика:

```text
Terra: high
Sol reviewer: medium
Sol escalation: high
DeepSeek Flash: default / economical
```

Если конкретный provider не поддерживает reasoning_effort:

- не эмулировать несуществующий параметр;
- использовать доступную конфигурацию;
- зафиксировать ограничение.

## 18. Безопасность shell/CLI

При вызове Codex CLI и Sol 5.6 Medium:

- использовать безопасный subprocess execution;
- избегать shell interpolation пользовательского текста;
- не передавать secrets внутри prompt;
- ограничивать working directory целевым проектом;
- логировать команду без токенов/секретов;
- сохранять stdout/stderr;
- обрабатывать timeout;
- обрабатывать non-zero exit code;
- не запускать destructive команды без необходимости.

Для потенциально destructive операций:

- сначала dry-run или анализ;
- затем явное решение главного агента.

## 19. Логирование

Добавить понятное логирование routing decisions.

Желательный формат:

```text
[ROUTER] task=project_research -> deepseek_subagent
[ROUTER] task=implementation -> codex_cli
[ROUTER] task=review -> sol_5_6_medium
[ROUTER] task=architecture_decision -> terra
[ESCALATION] reason=low_confidence -> sol_high
```

Не логировать скрытые chain-of-thought.

Логировать только:

- выбранного исполнителя;
- причину маршрутизации в кратком виде;
- task ID;
- результат выполнения;
- длительность;
- статус.

## 21. Тестовый сценарий после настройки

После реализации обязательно провести end-to-end тест.

Создать безопасную тестовую задачу в тестовом проекте или на минимальном изменении.

Проверить последовательность:

```text
User task
-> Terra
-> DeepSeek reconnaissance
-> Terra plan
-> Codex implementation
-> Sol 5.6 Medium review
-> Terra finalization
```

Отдельно протестировать Sol escalation:

```text
Terra
-> deliberate complex/ambiguous test case
-> ask_sol
-> Sol response
-> Terra consumes result
```

Также протестировать:

- failure DeepSeek;
- failure Codex CLI;
- failure Sol 5.6 Medium;
- failure Sol;
- provider timeout;
- malformed output;
- отсутствующий executable;
- rate limit.

Сбой одного исполнителя не должен приводить к потере основной Hermes session.

## 22. Acceptance Criteria

Работа считается завершённой, когда:

- [ ] Terra является основной моделью Hermes.
- [ ] Terra работает с high reasoning, если provider это поддерживает.
- [ ] DeepSeek Flash используется для стандартных subagents.
- [ ] Terra умеет явно делегировать research DeepSeek.
- [ ] Создан рабочий механизм Sol escalation.
- [ ] Terra может самостоятельно вызвать Sol при выполнении критериев.
- [ ] Sol не вызывается для обычных задач.
- [ ] Codex CLI вызывается Hermes для разработки.
- [ ] Sol 5.6 Medium вызывается Hermes для review/tests.
- [ ] Sol 5.6 Medium проверяет roadmap.
- [ ] Реализован ограниченный review/fix loop.
- [ ] Нет бесконечных циклов между Codex и Sol 5.6 Medium.
- [ ] Логируются routing decisions.
- [ ] Secrets не попадают в prompts/logs.
- [ ] Существующая конфигурация сохранена в backup.
- [ ] Проведён end-to-end тест.
- [ ] Проведён тест Sol escalation.
- [ ] Система восстанавливается после отказа отдельного executor.
- [ ] Существующие рабочие функции Hermes не сломаны.

## 22.1. Возврат Qwen в будущем

Текущая реализация должна быть модульной.

Когда лимиты Qwen CLI восстановятся, должно быть возможно:

1. заменить reviewer executor `Sol 5.6 Medium` на `Qwen CLI`;
2. не менять основную Terra orchestration;
3. не менять DeepSeek delegation;
4. не менять Codex development skill;
5. сохранить тот же структурированный review contract.

Reviewer должен быть абстрагирован от конкретной модели/CLI настолько, насколько это разумно для текущей архитектуры Hermes.

## 23. Что НЕ делать

Не нужно:

- делать Sol основной моделью;
- использовать Sol для каждого второго запроса;
- заменять Terra на DeepSeek;
- делать Sol Medium основным разработчиком;
- разрешать Codex самостоятельно менять scope;
- использовать случайный automatic model routing без контроля Terra;
- строить логику только на keywords;
- переписывать весь Hermes ради этой функции;
- создавать новый framework, если всё можно реализовать через штатные skills/tools;
- менять unrelated configuration;
- удалять текущие интеграции;
- менять рабочие API keys;
- публиковать secrets;
- считать fallback механизмом интеллектуальной эскалации.

## 25. Итоговая задача Hermes

Выполни всю работу самостоятельно.

Сначала проведи разведку текущей установки и существующих skills/config.

Затем:

1. составь короткий implementation plan;
2. внеси необходимые изменения;
3. создай недостающие skills/tools;
4. адаптируй существующие Codex/Sol Medium integrations;
5. настрой Terra как main orchestrator;
6. настрой DeepSeek как standard delegation model;
7. реализуй Sol expert escalation;
8. добавь routing rules;
9. добавь safeguards;
10. протестируй каждый компонент;
11. проведи end-to-end test;
12. исправь обнаруженные ошибки;
13. не останавливайся после создания файлов — проверь фактическую работоспособность.
